# Промпт: продолжение работ по аудиту ali.kg

Самодостаточный. Исходное задание аудита читать не нужно — всё, что от него
осталось живого, перенесено сюда **в проверенном виде**. Где формулировка
находки разошлась с кодом, стоит проверенный факт, а не исходная формулировка.

Дата сверки: **27.07.2026**, ветка `fix/audit-2026-07`, база — `main`.

---

## 0. РОЛЬ И РАМКА

Senior backend/frontend инженер. Стек: NestJS 11 + Prisma 5 + PostgreSQL
(`apps/api`), Next.js 16 App Router (`apps/web`), четыре SwiftUI-приложения
(`apps/ios`), Kotlin/Compose (`apps/android`). Монорепо на npm workspaces.

Ядро домена — append-only **Event Ledger** (`AuditEvent`): любая запись денег,
стока или статуса идёт транзакционно через `audit.transaction`, часто под
`pg_advisory_xact_lock` и `FOR UPDATE`. Это не стилистика, а инвариант: обойдёшь
— получишь расхождение, которое потом ищут вручную по проводкам.

Задача: закрыть оставшиеся находки production-аудита. Один коммит на находку,
номер находки в заголовке (`fix(F-07): …`).

## 1. ГЛАВНОЕ ПРАВИЛО — ОНО СТОИЛО ДОРОЖЕ ВСЕГО ОСТАЛЬНОГО

**Сверяй находку с кодом до того, как писать фикс.**

Не из осторожности — по статистике. Из восьми разобранных находок:

| Что оказалось | Сколько |
|---|---|
| Верна как описана | 2 |
| Верна по сути, но **диагноз неверен** | 3 |
| **Не воспроизводится вовсе** | 2 |
| Заблокирована внешними данными | 1 |

То есть **пять находок из восьми** нельзя было чинить по тексту задания.
Конкретно:

- **F-02** (утечка OTP в ответе API). Код уже содержал ровно ту защёлку, которую
  требовало задание. Дыру держала **конфигурация** — прод работал с
  `NODE_ENV != production`. Написать «фикс» по заданию значило закрыть тикет и
  оставить дыру открытой. Настоящая причина нашлась только потому, что я пошёл
  смотреть, почему `/api/metrics` отдаёт 200 без токена.
- **F-01**. Задание требовало ввести флаг `PAYMENTS_ONLINE_ENABLED`. Флаг не
  понадобился: `PAYMENT_PROVIDER=sandbox|production|none` уже существовал, и
  `none` — буквально запрошенное поведение. Новый флаг создал бы вторую точку
  правды о том же.
- **F-15**. Три «бага» курьерского контура оказались прогоном потока **без шага
  `POST /orders/:id/reserve`**. Существующий e2e покрывает тот же сценарий и
  проходит. Починка свелась к тексту ошибки, который эти «баги» и породил.
- **F-06** (в этом же промпте ниже). Задание говорит «мигрировать телефоны в
  serialized». В схеме нет режима, из которого их надо мигрировать: enum —
  `serialized | quantity`, **и оба дефолта уже `serialized`**.

Вывод, который надо унести: **отчёт «находка неверна, вот доказательство»
ценнее фикса несуществующего бага.** Второе создаёт мёртвый код и ложное
чувство закрытого тикета.

Если фактура расходится — **остановись и скажи**, не подгоняй и не расширяй
задачу, чтобы «хоть что-то починить».

## 2. КАК ПРОВЕРЯТЬ НАХОДКУ — ПОРЯДОК ДЕЙСТВИЙ

Не пропускай шаги 1–3, даже когда находка выглядит очевидной. Именно на
очевидных и вышли все пять расхождений.

1. **Прочитай код по месту.** Не `grep` по названию находки — открой файл и
   смежные. Половина расхождений видна за одну минуту чтения.
2. **Спроси: «а что, если это конфигурация, а не код?»** Проверь `.env.example`,
   `apps/api/.env`, `production-preflight.ts`, значения на живом проде через
   `curl`. F-02 — ровно этот случай.
3. **Спроси: «а нет ли уже механизма, делающего это?»** `grep` по смыслу, не по
   имени из задания: не `PAYMENTS_ONLINE_ENABLED`, а `PAYMENT_PROVIDER`,
   `gateway`, `sandbox`. F-01 — ровно этот случай.
4. **Воспроизведи.** Напиши тест, который падает **по причине из находки**.
   Не падает — находка не подтверждена, стоп, доложи.
5. **Только теперь чини** — минимальным диффом.
6. **Прогони полный гейт** (раздел 6), не точечные сьюты.

Отдельно: **найденное расхождение — тоже результат, и его надо закоммитить.**
Тест, фиксирующий «поток работает вот так», плюс запись в `PROGRESS.md`. Так
сделано с F-03 (`07bc92eb`) и F-15 (`d8d054c5`).

**F-06 — режим складского учёта у телефонов** ⚠️ **находка описана неверно**

*Заявлено:* «мигрировать телефоны и ноутбуки в `serialized`», предполагается
Prisma-миграция.

*Проверено — три факта, меняющие задачу целиком:*
1. Enum — `serialized | quantity`. Режима `bulk`, из которого якобы надо
   мигрировать, **не существует** ([`schema.prisma:168`](apps/api/prisma/schema.prisma:168)).
2. Дефолт `serialized` **и в схеме** ([`schema.prisma:625`](apps/api/prisma/schema.prisma:625)),
   **и в сервисе** ([`products.service.ts:160`](apps/api/src/products/products.service.ts:160)).
   Новый товар без явного указания уже создаётся serialized.
3. Смена режима при наличии остатков **уже запрещена** кодом —
   [`products.service.ts:230-242`](apps/api/src/products/products.service.ts:230),
   `ConflictError('tracking_mode_in_use')`, с проверкой `deviceUnit`,
   `inventoryBalance` и использования в наборах.

*Осталось:* **изменений в коде, скорее всего, нет.** Товары на проде получили
`quantity` явно — через API или ERP-интерфейс. Это операция с боевыми данными:
списать остаток → сменить режим → принять заново как IMEI-юниты. Порядок
продиктован самим гардом из п. 3.

*Действие исполнителя:* **не писать миграцию.** Проверить на проде, у каких SKU
`trackingMode = quantity`, и передать владельцу процедуру. Если найдётся путь,
которым режим выставляется в `quantity` без ведома оператора (дефолт в форме
ERP, импорт) — **вот это** и есть дефект, чини его.

## 6. ГЕЙТЫ — ТОЧНЫЕ КОМАНДЫ

Живой Postgres обязателен: без него тесты падают на старте, а не в ассертах.

Свой изолированный прогон (клонирует БД из шаблона, не мешает чужим):

```bash
npm run api:test:isolated
```

Один спек:

```bash
cd apps/api && NODE_PATH=./node_modules npx jest --runInBand --testPathPattern <name>
```

Типы (единственный статический гейт — ESLint и Prettier в проекте **нет**):

```bash
npx tsc --noEmit -p apps/api/tsconfig.json
```

Быстрый общий гейт:

```bash
npm run mvp:verify -- --skip-e2e
```

**Два разных гейта, и они расходятся.** CI гоняет `npm run api:test` — один
процесс. `mvp:verify` гоняет батчер — один спек-файл на процесс. Зелёный один
ничего не говорит о другом; перед релизом нужны оба.

**Полный гейт до коммита, а не после.** Я один раз прогнал только точечные
сьюты после F-01 и уронил два тест-модуля, которым понадобился новый провайдер
в DI. Поймал это следующим полным прогоном — то есть уже после коммита.

**Про красные тесты.** Гейт недетерминирован, это измерено: ~40% полных
прогонов дают 1–2 флакующих теста, каждый раз **в разных** сьютах. Порядок:
красное → перепрогони изолированно → воспроизвелось → дефект; не
воспроизвелось → флак, запиши в `BACKLOG.md` как `FLAKE-*`. Один зелёный
прогон тоже ничего не доказывает — повторяй.

## 7. ПРАВИЛА ПРИНЯТИЯ РЕШЕНИЙ

**7.1. Когда останавливаться и спрашивать.** Находка не воспроизводится;
фикс требует решения о продукте (роли, позиционирование, тарифы); нужны
внешние данные (спека шлюза, прод-логи); действие затрагивает боевые данные
или деньги. Стоп — это результат, а не провал.

**7.2. Изменение контракта API.** Витрина и офлайн-POS кэшируют схемы. Новое
обязательное поле ломает клиента, который его не шлёт. Порядок: добавить
необязательным → научить клиентов → сделать обязательным. Если так нельзя —
опиши почему и останови.

**7.3. Prisma-миграции.** Инварианты первыми, индексы и уникальности явно,
план отката до применения. Перед тем как писать миграцию, проверь, не решается
ли задача данными — F-06 ровно об этом.

**7.4. Новая колонка — крайнее средство.** По F-17 первая версия добавляла
`payoutStaffId`; выяснилось, что плательщик выводится из владельца смены,
уже связанной с аллокацией. Колонку откатил. Сначала ищи, где факт **уже**
записан.

**7.5. Не расширяй задачу.** Не рефактори «заодно», не трогай сид-данные, не
чини соседнее. Заметил постороннее — запиши в `BACKLOG.md` и иди дальше.

## 8. ФОРМАТ ОТЧЁТА

По каждой находке — строка:

| находка | коммит | тест | статус |
|---|---|---|---|

Статусы ровно четыре:
- **закрыто** — есть коммит и зелёный тест;
- **не воспроизводится** — есть тест, фиксирующий фактическое поведение;
- **блокировано** — назван блокер и кто его снимает;
- **не начато**.

**Не помечай «закрыто» без зелёного теста.** «Сделано, но тест не успел» — это
«не начато».

Итоги — в существующие журналы: `PROGRESS.md`, `BACKLOG.md`,
`docs/READINESS.md`. **Новый changelog не заводить.**

## 9. ЗАПРЕТЫ

- **Не ослабляй существующее:** серверный repricing, idempotency-keys, OTP-lock,
  rate limits, refresh-rotation, RBAC-guards, четырёхглазые согласования,
  advisory-локи. Если фикс требует ослабить защиту — это не тот фикс.
- **Не пиши деньги/сток/статусы мимо `audit.transaction`.**
- **Секреты только в env**, документация — в `.env.example`. В репозиторий не
  попадают даже тестовые учётные данные.
- **Никаких `TODO: разберусь потом`.** Не можешь закрыть — опиши блокер и
  остановись. Незакрытая задача с честным блокером лучше закрытой заглушкой.
- **`git add <путь>` берёт файл целиком.** В дереве параллельно работает второй
  инструмент. Сверяйся с `git status`, снятым **до** начала работы, иначе
  заберёшь чужие незавершённые правки в свой коммит — так уже случилось
  (`COMMIT-HYGIENE-182`: в мои коммиты уехал чужой Cloudflare-блок в
  `package.json` и правка `resolveApiBase`).
- **Не удаляй боевые данные без согласования** (см. L-8).
